# mrX 文档编写与维护规范

> 本文面向 mrX 文档维护者。第一次使用 mrX 时请先阅读 [文档入口](README.md)，不要从本文开始。

## 1. 文档组织

模块文档按源码职责分目录，文件名与模块或工具名称对应：

```text
document/
├── README.md            # 阅读入口与文档索引
├── usage.md             # 框架接入与快速开始
├── kernel/              # 内核模块
├── libc/                # C 库
├── drivers/             # 设备驱动
├── fs/                  # 文件系统
├── modules/             # 上层组件
├── platform/            # 平台移植层
├── scripts/             # 主机端工具
└── test/                # 测试框架
```

[README](README.md) 是唯一的入口与目录导览，承担三件事：说明 mrX 的定位、给出阅读路线、维护完整索引。
它面向使用者，措辞以“先做什么、做完看到什么”为主，不放维护者细节。

- 文档路径与源码职责保持对应，例如 `kernel/timer.md` 对应 `kernel/timer.c`。
- 每个模块文档开头标注对应的 `MR_USE_*` 功能宏；没有功能宏时写明“无（始终编译）”。
- 新增、删除或重命名文档后，同步更新 [README](README.md) 的完整文档索引，并检查目录结构说明是否仍然准确。
- 生成文件、构建产物和临时材料不放入文档目录。

### 1.1 骨架的适用范围

第 2 节的骨架针对 **固件模块文档**（内核服务、C 库、设备驱动、文件系统、上层组件、测试框架）。 以下两类不受该骨架约束：

- **入门与索引类**：`README.md`、`usage.md`。它们按使用者任务自行组织章节，不套用用户/开发者分节。
- **主机端工具类**：`scripts/` 下的教程（含 `scripts/README.md`）。它们描述 Python 工具的输入输出， 没有 `MR_USE_*`
  功能宏与头文件，因此不要求元数据表，也不要求用户/开发者分节； 按“用法 → 参数 → 排错”组织即可，需要时可自建目录与小型开发者说明（如
  `scripts/cli.md`）。 其中 `scripts/cli.md` 是唯一示例性保留分节的工具文档，属自愿而非强制。

目录入口文件（如 `kernel/README.md`、`scripts/README.md`）只需给出该目录的模块清单和阅读顺序， 同样不套用骨架。

## 2. 模块文档骨架

模块文档按“用户指南 → 开发者指南”组织。用户先看前半部分即可正确使用模块，只有需要理解或修改实现时再阅读后半部分。

```markdown
# 模块名（英文标识符）

> 一句话说明模块解决的问题。

| 项目     | 说明                      |
|----------|---------------------------|
| 功能宏   | `MR_USE_XXX`              |
| 头文件   | `<mrX/.../mr_xxx.h>`      |
| 依赖模块 | [模块](../path/module.md) |

---

## 用户指南

### 1. 模块概述

### 2. 配置与依赖

### 3. 快速上手

### 4. 使用说明

### 5. API 参考

### 6. 完整示例

### 7. 常见问题（FAQ）

---

## 开发者指南

### 8. 架构总览

### 9. 数据结构

### 10. 核心流程

### 11. 并发与中断安全

### 12. 扩展与派生

### 13. 源码导读

### 14. 附录
```

模块较小时可以合并不适用的章节，但必须保留用户内容和开发者内容的分界；章节编号按实际内容调整。

## 3. 用户篇与开发者篇的边界

- 用户篇说明做什么、怎么调用、生命周期和可观察行为；不要求读者了解链表、锁或内部源码。
- 开发者篇说明架构、数据结构、实现原因、并发约束和扩展方法，可以引用源码位置。
- 同一行为只在用户篇定义一次；开发者篇解释其实现原因，不重复改写用户约定。
- 正文使用中文；API、宏、配置项、文件名和代码保持原样。

## 4. 示例与 API 描述

- 示例必须来自 `mrX/test/`，或能按当前公开 API 直接编译；禁止虚构 API。
- 示例只保留说明主题所需的内容，省略错误处理时要明确说明。
- 示例使用的 `MR_USE_*` 和 `MR_CFG_*` 必须在“配置与依赖”中解释。
- API 表格按初始化与销毁、控制、参数与查询、引用管理等功能分组，列固定为“API | 说明”。
- 每个 API 在表格下给出原型、参数、返回值和注意事项，内容必须与头文件注释一致。
- 返回值统一说明：`0` 表示成功；负数是错误码；指针返回 `MR_NULL` 表示失败。

## 5. 交叉引用与维护

- 文档之间使用相对路径；例如，在 `kernel/` 内互相引用写 `[时钟](clock.md)`，跨目录时按当前文件位置计算路径。
- 源码引用使用 `` `mrX/kernel/timer.c:98` ``；行号变化后，以函数名为主要锚点并及时修正辅助行号。
- 修改公开 API、配置项或已实现行为时，同步更新对应文档。
- 不把未确定的实现细节写成已实现行为；避免用“大概、可能、应该”描述确定性行为。
- 提交前检查新增链接、配置名、头文件名和示例是否仍与源码一致。
- 提交前额外确认 [README](README.md) 中的索引条目和目录导览没有过期。
