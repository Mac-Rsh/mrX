# mrX 文档编写规范

本文面向 mrX 文档维护者，规定文档目录组织、结构模板与写作风格。阅读或接入 mrX
请直接看 [文档入口](README.md)。

---

## 1. 目录组织

`document/` 按源码职责分目录，尽量与源码路径一一对应：

```text
document/
├── README.md          # 总入口与模块索引
├── usage.md           # 框架接入与快速开始
├── documentation.md   # 本规范（维护者参考）
├── kernel/            # 内核基础服务（含目录入口 README.md）
├── libc/              # C 基础库
├── drivers/           # 设备驱动（<driver>.md + porting.md + 扩展芯片）
├── fs/                # 文件系统（VFS、RamFS、RootFS）
├── modules/           # 上层组件（Boot、Crypto、RPC、XVM）
├── platform/          # 平台移植层与端口契约
├── arch/              # 厂商级适配规范（芯片具体说明在 mrX/arch/<vendor>/<target>/README.md）
├── scripts/           # 主机端 CLI 工具（含目录入口 README.md）
└── test/              # 测试框架
```

新增、重命名或删除文档后，需同步更新 [README.md](README.md)（及对应目录入口）中的索引链接。

---

## 2. 写作风格

1. **说人话，去掉模板腔**：不用“XXX
   解决的问题是：……”、“做完之后你应该有什么”、“不适用于：……”这类机械套话；直接讲清楚模块干什么、怎么用、有什么限制。
2. **克制篇幅，先用后懂**
   ：调用者关心的是配置、示例、生命周期和踩坑点；内部链表、锁实现、源码导读放到文末“内部实现”小节，简单模块可以不写内部实现。
3. **不复述代码**：代码块里的行内注释能讲清楚的，正文不再重复一遍；`get`/`set`
   这类自明接口在表格里写清即可，不必逐个展开长段说明。
4. **善用表格和图示**：配置项、API 列表、状态流转优先用表格、ASCII 图或 Mermaid
   图，减少大段文字堆砌。
5. **只写确定的事实**：所有宏、API 签名、配置项、CLI 参数必须与当前头文件、Kconfig
   和源码一致。

---

## 3. 排版规范

- **段落不硬换行**：一个自然段写在同一行内，禁止按固定列宽截断中文句子、标点或
  Markdown 标记（如 `**`、`` ` ``）。
- **代码块**：统一使用 ```` ```c ````、```` ```text ````、```` ```bash ````、
  ```` ```mermaid ````，不使用 `~~~`。
- **源码引用**：引用文件或函数符号（如 `kernel/timer.c` 中的 `mr_timer_start`
  ），不写容易随提交失效的精确行号。
- **交叉引用**：文档间使用相对路径，并保持与实际文件名一致。

## 4. 文档结构模板

不同类别的文档按实际需要选择对应结构，不强行凑齐空白章节。

### 4.1 固件模块文档（`kernel/`、`libc/`、`drivers/<drv>/<drv>.md`、`fs/`、

`modules/`）

```markdown
# 模块中文名（EnglishName）

一两句话说明模块用途与核心能力。

| 项目 | 说明 |
|---|---|
| 功能宏 | `MR_USE_XXX`（无则写“无，始终编译”） |
| 头文件 | `<mrX/.../mr_xxx.h>` |
| 依赖 | [依赖模块](../path/module.md) |
| 测试 | `test/.../xxx.c`（无则省略） |

## 配置

（仅列需要关注的配置项，无配置项时省略本节）

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `MR_USE_XXX` | bool | n | ... |

## 快速上手

（一个简洁、可对照使用的完整 C 片段，关键步骤用简短注释说明）

## 核心机制与约束

（生命周期、工作模式、回调上下文、线程/中断安全及常见错误用法）

## API 速查

（按功能分组列 `API | 说明`；仅对参数复杂、返回值特殊或有隐含语义的接口在表下补充说明）

## 内部实现（可选）

（非平凡模块在此补充架构图、数据结构、并发保护与关键源码路径）
```

### 4.2 外设扩展芯片文档（如 `drivers/gpio/gpio_hc595.md`）

复用标准驱动 API 的扩展芯片，不重复介绍公共接口，按以下轻量结构编写：

```markdown
# 芯片/扩展名（EnglishName）

一句话说明适配的硬件及其呈现的驱动类型。

| 项目 | 说明 |
|---|---|
| 启用方式 | 随 `MR_USE_DRIVER_XXX` 编译，由 HardTree `compat` 节点触发 |
| 头文件 | 复用 `<mrX/drivers/xxx/mr_xxx.h>` |

## HardTree 属性

（表格列出必需与可选属性）

## 快速上手

（查找、setup 及调用公共驱动 API 的短示例）

## 运行语义与限制

（如影子寄存器、阻塞特性、不支持的功能等）
```

### 4.3 驱动移植文档（`drivers/<driver>/porting.md`）

面向 backend 开发者，不重复用户 API，也不描述具体芯片寄存器：

1. **移植边界**：公共层负责什么，backend 负责什么。
2. **操作表（ops）**：必需回调与可选回调清单、参数与返回值约定。
3. **关键契约**：调用上下文（线程/ISR）、缓冲区/内存归属、事件上报机制。
4. **HardTree 安装**：通用安装宏与标准属性。
5. **验收要点**：移植完成后的基本验证项。

### 4.4 主机端脚本文档（`scripts/<tool>/<tool>.md`）

按 **用途 → 常用命令 → 参数说明 → 输出与排错** 组织，无需功能宏与头文件元数据表。
