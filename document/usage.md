# mrX 框架使用指南（Usage）

> 这篇是接入 mrX 的主线：从准备环境、配置功能、描述硬件，一直到框架跑起来。
> 如果你还不知道 mrX 是什么、该从哪篇开始读，先看 [文档入口](README.md)。
> 平台移植、`arch/` 目录组织和 `install.toml` 编写属于 [平台移植层 Platform](platform/platform.md)，
> 本文不展开。各功能模块的完整 API 见 [文档总索引](README.md)。

| 项目     | 说明                                                                        |
|----------|-----------------------------------------------------------------------------|
| 适用对象 | 已有应用工程、准备接入并使用 mrX 的开发者                                   |
| mrX 目录 | 框架源码及生成文件；应用代码由使用者自己的工程管理                          |
| 主机工具 | Python 3.11+，依赖见 `mrX/scripts/requirements.txt`                         |
| 相关文档 | [CLI](scripts/cli/cli.md)、[Platform](platform/platform.md)、各模块用户指南 |

## 1. 开始之前，你需要准备什么

接入 mrX 不用做太多准备，但下面这几样最好提前确认，能省掉大半的排查时间：

- **一个能编译的应用工程**。用你现有的就行，mrX 只是往里加一份依赖。
- **主机上的 Python 3.11 或更新版本**，以及 `mrX/scripts/requirements.txt` 里的依赖。 先跑一次安装命令，之后再用 CLI
  就不会卡在缺包上：

  ```text
  python -m pip install -r ./scripts/requirements.txt
  ```

- **一个匹配目标环境的平台适配**。mrX 自己不知道你们板子的 tick、中断和串口怎么用，这些由平台层提供。
  选择与安装见 [Platform](platform/platform.md)。
- **知道目标板的硬件信息**（引脚、外设、地址）。只有使用硬件树驱动时才需要，但它决定了 HTC 那一步能不能做对。

> 顺序上有一条容易踩的坑： **平台要装在配置之前**。因为平台会在 Kconfig 里注册自己的选项，
> 先装平台，配置界面里才会出现它们。

<!-- -->

> 本文所有命令都假设当前目录是 mrX 框架根目录，即包含 `Kconfig` 和 `scripts/cli.py` 的 `mrX/` 目录。写路径时按这个前提来。

## 2. 从零开始的使用流程

下表第 1～6 步走完，mrX 就在你的工程里跑起来了。每步都标了"做完之后你应该有什么"，方便对照：

| 步骤 | 做什么               | 做完之后                                        | 详细说明                            |
|------|----------------------|-------------------------------------------------|-------------------------------------|
| 1    | 准备平台             | `platform/` 下出现目标平台的适配文件            | [Platform](platform/platform.md)    |
| 2    | 配置功能             | 生成 `include/mrX/mr_config.h`                  | [第 3 节](#3-使用-kconfig-配置功能) |
| 3    | 编译硬件描述（可选） | 生成 `include/mrX/mr_hardgen.h`                 | [第 4 节](#4-htc-硬件描述编译)      |
| 4    | 纳入应用构建         | 工程能编译出 mrX 的源码                         | [第 5 节](#5-把-mrx-纳入你的构建)   |
| 5    | 确认注册段处理       | 链接脚本保留、聚合了注册段（MDK 无需额外处理）  | [第 6 节](#6-注册段与-sections)     |
| 6    | 启动框架             | `mr_user_init()` 返回，初始化函数按注册顺序执行 | [第 7 节](#7-启动框架)              |
| 7    | 按需接入模块         | 外设、文件系统、RPC 等工作起来                  | [模块文档](README.md)               |

几个不那么明显但很重要的前提：

- **第 3 步是可选的**。只有用硬件树驱动或板级描述时才需要 HTC；不写硬件描述也能正常用 mrX。
- **第 4 步的收集范围决定链接结果**。源码必须 **逐个 `.c` 收集成对象文件再链接**，不能先打成静态库——注册段只有在目标文件级参与链接时才会被保留。
- **第 5 步的分工取决于工具链**。GNU ld 风格链接器需要手工处理；Keil MDK 不运行本节的 `sections` 脚本，armlink
  默认即按名字连续放置这些注册段，无需额外配置。
- **换了平台或改了硬件描述之后**，第 2、3 步要重新执行，并让应用工程用上最新生成的头文件。 生成文件是产物，不要手动去改它——改了下次生成就被覆盖。

## 3. 使用 Kconfig 配置功能

mrX 用 Kconfig 管理功能开关和资源参数。你只需要记住两类宏：

- `MR_USE_*`：某个模块 **要不要编译进来**。
- `MR_CFG_*`：编译进来之后，它 **有多少资源可用**（缓冲区大小、最大对象数之类）。

模块之间的依赖关系由 Kconfig 自动处理，你不用手工维护。

### 3.1 正常流程：使用 UI

在 mrX 目录运行：

```text
python ./scripts/cli.py kconfig
```

命令会打开 menuconfig 界面。用方向键移动、回车进入子菜单、空格切换选项，改完保存退出即可。 脚本会自动维护 `.config`，并生成
`include/mrX/mr_config.h`。想接着上次改，直接再运行一次同样命令。

第一次就卡在打不开界面上？多半是缺依赖或终端不支持。按 [CLI](scripts/cli/cli.md) 检查 menuconfig 依赖。

怎么选才不容易出错：

- 先按模块文档的"配置与依赖"一节，把需要的模块打开，再根据目标板资源调参数。
- 被其他选项依赖、或者被 `select` 选中的选项，不能脱离依赖单独关掉。
- 拿不准最终状态时，看 UI 里显示的值——保存时以它为准，不要凭记忆。

### 3.2 非交互场景：使用 `--no-ui`

只有在当前环境不方便操作 menuconfig 时（比如自动化脚本，或者让 AI 代为修改）才用这个模式：

```text
python ./scripts/cli.py kconfig --no-ui
```

它不打开界面，而是读取已有的 `.config` 并生成配置头； **`.config` 不存在时会直接报错**。

直接编辑 `.config` 是非交互场景的备用手段。改完之后仍然要重新运行命令，让 Kconfig 解析依赖关系并重新生成 `mr_config.h`
；遇到依赖冲突时还是得回到 UI 里修正。

常用路径可以用 `-k/--kconfig`、`-c/--config` 和 `-o/--output` 覆盖，具体选项见 [CLI](scripts/cli/cli.md)。

## 4. HTC 硬件描述编译

HTC（Hardware Tree Compiler）是 mrX 的硬件描述入口。它把 DTS 风格的 `.hts` 或 `.htsi` 文件编译成 C 头文件， 让驱动能按节点路径、
`label`、`alias` 和 `compatible` 去实例化，读取板级硬件信息。

它做的事是把"这块板子上有什么硬件"写成一次描述，让驱动自己去找设备，不用在 C 代码里硬编码。

### 4.1 基本流程

准备好与目标板匹配的硬件描述文件后，在 mrX 目录运行：

```text
python ./scripts/cli.py htc -i <硬件描述>.hts
```

默认输出为 `include/mrX/mr_hardgen.h`。启用驱动框架后，驱动实现只要包含 `<mrX/drivers/mr_driver.h>`
就能拿到硬件树宏，不需要再显式包含 `<mrX/drivers/mr_hardtree.h>`；具体怎么实例化由对应驱动文档说明。

### 4.2 描述文件与生成结果的约定

- 节点、属性、`label`、`alias`、`status` 和 `compatible` 必须反映真实硬件。 **不要照抄其他板卡的引脚或外设属性**——HTC
  不会替你发现这类错误，它只会忠实地编译你的描述。
- `status` 会影响驱动实例的初始化级别；被禁用的节点不会被当成可用设备。
- 用 `#include` 拆分描述文件时，通过 `-I <目录>` 增加包含搜索路径，可以重复指定。
- 默认使用外部 C 预处理器；环境里没有该预处理器时用 `--no-cpp`。需要检查非标准扩展时加 `--strict`。
- 改了 `.hts`、包含文件或平台硬件属性后，重新运行 HTC。 **生成的头文件必须和当前配置、当前硬件描述一致**。

`.hts` 属于应用或板级资产，放在哪由你自己决定，用 `-i` 显式告诉 HTC 就行。 HTC
本身可以独立生成头文件；只有启用驱动框架并使用硬件树驱动或板级描述时，应用才需要用到生成结果。 语法和 `MR_HT_*`
宏的完整说明见 [驱动框架](drivers/driver.md) 及各具体驱动文档。

## 5. 把 mrX 纳入你的构建

这一步把 mrX 真正接进你的工程文件。mrX 仓库不接管你的构建系统，所以需要手工加两项： **头文件搜索路径**和 **源码收集范围**。

**头文件路径**只加一个：

```text
<mrX>/include
```

`<mrX>` 指框架根目录（含 `Kconfig` 和 `scripts/cli.py` 的那个 `mrX/`），下同。平台、内核、驱动、C 库的头文件都在这一层之下，
`#include <mrX.h>` 或 `#include <mrX/kernel/mr_timer.h>` 都能直接解析。

**源码收集范围**是框架各子目录下的全部 `.c`：

```text
<mrX>/kernel/*.c
<mrX>/libc/*.c
<mrX>/drivers/*.c
<mrX>/fs/*.c
<mrX>/modules/*.c
<mrX>/platform/*.c
```

四条容易出错的边界：

- **用递归收集**（如 CMake 的 `GLOB_RECURSE`、工程工具的“添加文件夹”），不要只加目录顶层——`drivers/gpio/`、`fs/` 这类子目录才是主体。
- **不要收集 `mrX/arch/`**。它是适配仓库，不是编译单元；真正参与编译的是安装后的 `<mrX>/platform/`。两者同时进工程会因重复符号而链接失败。
- **不要收集 `mrX/test/`**，除非你确实要跑单元测试（见 [测试框架](test/test.md)）。
- **不要先打成静态库再链接**。注册段（initcall、驱动、RPC）靠链接器在 **目标文件级**
  保留和聚合；先归档会把"只被注册段引用"的对象整段丢掉，现象是"代码写了却不执行"。工程里应把 mrX 的 `.c` 作为对象文件或
  `OBJECT` 库直接参与最终链接。

生成文件 `<mrX>/include/mrX/mr_config.h` 和 `mr_hardgen.h` 按普通源文件对待即可，让应用工程能编译到它们；改配置或改硬件描述后重新生成，不要手工补丁。

Keil MDK 工程用 [MDK 工程维护](scripts/mdk/mdk.md) 的 `mdk` 命令把文件同步进工程组，收集范围同样是上面这六项。

> 为什么这一步排在这里：第 3 步生成的头文件必须先存在，工程才编得过；而注册段要在 **链接**阶段才被收集，所以下一步才是它。

## 6. 注册段与 sections

mrX 用注册段来保存 initcall、驱动、RPC 和测试用例等信息，相当于一张"启动时要执行哪些函数"的清单。 代价是：
**链接器必须保留并收集这些段**，否则框架启动时看不到任何注册项，表现为"代码明明写了却没被执行"。

### 6.1 GNU ld 风格链接脚本

使用 GNU ld 风格链接脚本的工程，在准备好自己的链接脚本后运行：

```text
python ./scripts/cli.py sections -i <用户链接脚本>.lds
```

默认使用 mrX 根目录的 `sections.toml`；需要自定义段描述时用 `-c <段描述文件>` 指定。 命令会 **原地更新**
链接脚本，所以重复执行是幂等的，多跑几次没关系。

用的是其他链接器？那就按该链接器的语法，自己实现同等的保留、聚合和排序规则， 不要把 GNU ld 的命令直接套过去。

### 6.2 Keil MDK 等特殊环境

Keil MDK 工程不需要手工执行 `sections`：注册段常量带有 `used` 属性，armlink 默认会保留并按名字连续、有序放置它们，无需
scatter 或链接器选项；其余配置遵循 MDK 自身的集成方式。机理与注意事项详见
[Keil MDK 工程维护](scripts/mdk/mdk.md) 的"注册段与链接器"一节。

顺带说明一个容易混淆的点：`mdk` 命令是用来维护 MDK 工程文件的， **和注册段处理无关**。 其他工具链或工程管理器如果有自己的段收集机制，优先遵循那套环境的做法。

## 7. 启动框架

### 7.1 初始化

应用底层启动完成后，调用一次 `mr_user_init()`。它会先初始化平台和已启用的内核服务， 再按注册段执行框架及应用初始化函数。所以：

- 你 **不需要**另外调用 `mr_kernel_init()` 或 `mr_platform_init()`。
- 需要按 initcall 自动初始化应用资源时，按 [初始化调用](kernel/initcall.md) 注册用户级初始化函数即可。

启用 `MR_USE_ENTRY` 后，ARMCC 分支通过 main 包裹机制调用 `mr_kernel_init()`；其他工具链需要把板级启动接到 `mr_entry()`
，由它完成内核初始化并调用 `main()`。这 **不会替代** `mr_user_init()`
。如果应用需要执行用户 initcall，仍然要在自己的入口调用一次
`mr_user_init()`，只是不必重复调用内核或平台初始化函数。

写初始化函数时注意一点：函数应该 **做完准备工作就返回**。不要在里面占用主循环， 也不要等待一个可能永远不满足的条件——否则排在它后面的初始化项都不会执行，
而现象看起来会像是"某些模块莫名没生效"。

## 8. 常见问题排查

| 现象                         | 优先检查                                                                                                    |
|------------------------------|-------------------------------------------------------------------------------------------------------------|
| 找不到平台头文件或实现       | 是否按 [Platform](platform/platform.md) 安装了目标适配，并使用了安装后的 `platform/`                        |
| 修改配置后功能没有变化       | 是否通过 UI 保存并生成了最新 `mr_config.h`；非交互模式是否读取了正确的 `.config`；配置是否受依赖约束        |
| HTC 生成失败或驱动找不到实例 | 输入文件和 `-I` 路径是否正确；`compatible`、节点状态和属性是否与驱动要求一致；是否重新生成了 `mr_hardgen.h` |
| 初始化函数没有执行           | 是否调用 `mr_user_init()`；注册段是否已由工具链保留并收集；初始化函数是否被放入正确的用户级别               |
| 链接报重复符号               | `mrX/arch/` 与安装后的 `platform/` 是否被同时收进了工程（只应收集后者）                                     |
| 没有日志或 printf 输出       | 是否启用相应功能；平台输出接口是否连接到终端；消息是否被日志级别过滤                                        |

排查时先分清问题落在哪个阶段：

1. **平台阶段** —— 头文件、实现文件、tick 和输出接口是不是齐的。
2. **配置阶段** —— 功能是不是真的开上了，生成头文件是不是最新的。
3. **生成阶段** —— `mr_hardgen.h` 和当前 `.hts` 是不是一致的。
4. **构建阶段** —— 源码收集范围是不是第 5 节那六项，有没有误收 `arch/` 或 `test/`。
5. **初始化阶段** —— 注册段有没有被链接器收集，初始化函数有没有被执行。

这五步排除掉之后再谈运行期问题，去看对应模块的用户指南和 FAQ。 一个实用习惯：改完 `.hts` 或配置后 **重新生成一次**
再复现问题，比对着旧产物反复怀疑代码快得多。

## 9. CLI 速查

以下命令均从 mrX 目录执行：

| 命令                                             | 用途                                                        |
|--------------------------------------------------|-------------------------------------------------------------|
| `python ./scripts/cli.py kconfig`                | 打开 UI 配置并生成 `mr_config.h`                            |
| `python ./scripts/cli.py kconfig --no-ui`        | 非交互读取 `.config` 并生成 `mr_config.h`                   |
| `python ./scripts/cli.py htc -i <file>.hts`      | 编译硬件描述并生成 `mr_hardgen.h`                           |
| `python ./scripts/cli.py sections -i <file>.lds` | 为 GNU ld 风格链接脚本注入注册段规则                        |
| `python ./scripts/cli.py platform ...`           | 安装、卸载或查看平台；详见 [Platform](platform/platform.md) |

忘了有哪些命令时，`python ./scripts/cli.py list` 可以列出全部子命令，
`python ./scripts/cli.py help <command>` 查看单个命令的用法。需要连续执行多条命令时， 不带命令运行
`python ./scripts/cli.py` 即可进入交互模式（全局选项如 `-h`、`--version`
要写在命令名之前）。

更多参数和交互式 shell 用法见 [CLI](scripts/cli/cli.md)。
